# Functional Specification: HITL Candidate Feedback API (FR-7)

## 1. Purpose
The Human-in-the-Loop (HITL) Feedback API allows human reviewers to provide qualitative and quantitative feedback on candidate matches generated by the AI matching engine. This data is critical for system auditing, manual override tracking, and future model recalibration.

## 2. API Definition

### 2.1 Endpoint
`POST /api/v1/requisition/match/feedback`

`GET /api/v1/requisition/match/feedback/{correlation_id}/{team_member_id}`

### 2.2 Request Payload (JSON)
```json
{
  "team_member_id": "string",
  "correlation_id": "uuid",
  "reviewer_email": "string",
  "liked": "boolean",
  "rating": "integer (1-5)",
  "comment": "string (optional)"
}
```

### 2.3 Response (JSON)
- **Success (201 Created / 200 OK)**:
  ```json
  {
    "status": "success",
    "action": "created | updated",
    "feedback_id": "integer"
  }
  ```
- **Error (400 Bad Request)**: Invalid payload or rating out of range.
- **Error (401 Unauthorized)**: Missing or invalid authentication token.
- **Error (403 Forbidden)**: `reviewer_email` mismatch with authenticated user.
- **Error (429 Too Many Requests)**: Rate limit exceeded (20 req/min).

### 2.4 GET / Retrieve Feedback Response

- **Success (200 OK)**:
  ```json
  {
    "status": "success",
    "feedback": [
      {
        "team_member_id": "string",
        "correlation_id": "uuid",
        "reviewer_email": "string",
        "liked": true,
        "rating": 3,
        "comment": "string",
        "created_at": "iso8601",
        "updated_at": "iso8601"
      }
    ]
  }
  ```
  The list may be empty if no feedback exists for the given match.

## 3. Business Rules

### 3.1 Authorization
- The API SHALL require a valid JWT via OAuth2.
- The `reviewer_email` in the payload MUST exactly match the `email` or `sub` claim in the authenticated token.

### 3.2 Idempotency & Persistence (UPSERT)
- Multiple submissions for the same `(team_member_id, correlation_id, reviewer_email)` MUST result in an update to the existing record rather than a new insertion.
- The `updated_at` timestamp MUST be updated on every modification.

### 3.3 Data Integrity
- `rating` MUST be an integer between 1 and 5 (inclusive).
- `team_member_id` and `correlation_id` MUST be valid identifiers.

## 4. Performance & Scrutiny
- **Rate Limiting**: 20 requests per minute per reviewer to prevent spamming.
- **Latency**: P95 < 200ms for feedback submission.

## 5. Persistence Expectations
- Data MUST be stored in the `requisition_match_team_member_feedback` table.
- All writes MUST be transactional.
