## 1. The Problem We Started With

Before this sprint the AI pipeline had three compounding issues that were silently producing
wrong results on almost every real request:

**Issue A — `jd_level_vector` embedded the wrong text.**
The vector that drives the semantic gate and contributes 25 % of the `match_score` was being
built from `"Job level: Backend Engineer"`. The value came from `normalized_role` — the domain
category, not the seniority level. A junior and a senior backend engineer would produce
identical `jd_level_similarity` values, so the gate was useless for seniority filtering.

**Issue B — The RAG SQL issued a single-vector distance query.**
`multi_vec_semantic` was described in the spec as a 5-vector composite, but the actual SQL only
computed one `<->` distance — the `full_jd_vector`. The level, mandatory, preferred, and cert
vectors were generated by Node 3 but never used in retrieval. The cert distance column was
fetched from pgvector but then dropped on the floor.

**Issue C — `skills_text` was NULL for all seed candidates.**
The `INSERT INTO team_member_embeddings` statement in `scripts/seed_candidates.py` never
included the `skills_text` column. BM25 keyword search (`ts_rank`) reads `skills_text` first;
with it NULL, keyword scores were identical for every candidate regardless of their skills.
Additionally, the embedding vectors were deterministic random noise (hash-based), so semantic
scores were meaningless for testing.

## 2. 11 May — Core Algorithm Fixes

### 2a. Fix: Seniority Level Inference in JD Parsing

**Commit:** `ae8a036` — *fix: infer seniority level in JD parsing and fix jd_level_vector text*

**Files changed:** `src/app/ai/agents/requisition_parsing.py`, `src/app/ai/utils/embedding.py`,
`src/app/ai/agents/embedding.py`

#### The bug

`jd_level` was set like this in `embedding.py`:

```python
jd_level=parsed_jd.get("normalized_role", ""),   # "Backend Engineer"
```

And then the text for the level vector was:

```python
jd_level_text = f"Job level: {jd_level}"
# Result: "Job level: Backend Engineer"
```

`"Backend Engineer"` carries zero seniority signal. The vector was effectively a second
domain-category vector, nearly identical to `full_jd_vector`.

Additionally, the LLM in Node 1 (requisition parsing) had never been asked to extract a
seniority level. The downstream code that selected scoring weights and gates
(`parsed_jd.get("level", "MID")`) therefore always got `"MID"` regardless of the actual job.

#### The fix

**Step 1 — LLM prompt.**
Added `"level": "JUNIOR | MID | SENIOR"` to the LLM output schema in `requisition_parsing.py`
with explicit inference rules:

```
Level inference rules:
- SENIOR: title contains Senior/Sr/Lead/Principal/Staff/Architect, OR 5+ years required
- JUNIOR: title contains Junior/Jr/Associate/Entry/Intern/Graduate, OR <= 1 year required
- MID: everything else, or when uncertain.
```

**Step 2 — Four-layer fallback chain.**
Added `_resolve_level()` which runs after the LLM call:

```python
def _resolve_level(llm_level, title, min_months) -> str:
    return (
        (llm_level.upper() if llm_level in {"JUNIOR","MID","SENIOR"} else None)
        or _infer_level_from_title(title)      # keyword scan on normalized_title
        or _infer_level_from_experience(min_months)  # >= 60 months → SENIOR, <= 12 → JUNIOR
        or "MID"
    )
```

The chain means:
- If the LLM returns a valid level, use it (most reliable).
- If the LLM fails or returns garbage, title keywords catch obvious cases ("Senior Python Dev" → SENIOR).
- If the title is ambiguous ("Software Developer"), experience range breaks the tie.
- If everything is absent, default to MID (industry standard for unqualified titles).

**Step 3 — Fix `jd_level_text`.**
Changed the text that gets embedded for the level vector:

```python
# Before:  "Job level: Backend Engineer"
# After:   "Seniority: SENIOR. Title: Senior Backend Engineer."
```

This gives the embedding model actual seniority vocabulary so that `jd_level_similarity` now
measures career-level alignment — a senior engineer embedding is semantically far from a junior
embedding on this vector — rather than domain category overlap.

**Step 4 — Wire `level` into the pipeline.**
Changed `embedding.py` to pass the newly inferred level:

```python
jd_level=parsed_jd.get("level", "MID"),   # was: normalized_role
```

#### Impact

- Scoring gate and weights now use the correct role config (JUNIOR/MID/SENIOR) instead of
  always using MID defaults.
- `jd_level_similarity` now meaningfully discriminates seniority — a junior candidate on a
  Senior requisition will score lower on the level gate as intended.
- Callers that omit `level` in the API input still get correct inference from `jd_text`.

### 2b. Feat: Multi-Vector Hybrid Search in RAG Retrieval

**Commit:** `0cca4b9` — *feat: multi-vector hybrid search in RAG retrieval*

**Files changed:** `src/app/ai/utils/rag_retrieval.py`, `src/app/ai/agents/rag_retrieval.py`,
`src/app/settings.py`

#### The bug

The old SQL query was:

```sql
SELECT e.embedding <-> CAST(:vector AS vector) AS similarity_score,
       ts_rank(...) AS keyword_score
FROM team_member_embeddings e
ORDER BY similarity_score ASC
```

It used only `e.embedding` (a single 768-dim vector equivalent to `full_jd_vector`) for
semantic scoring. The four additional vectors generated by Node 3 — level, mandatory, preferred,
cert — were simply never queried. All the embedding work in Node 3 for those vectors was wasted.

#### The fix

The new SQL issues **five separate `<->` distance comparisons** in a single query:

```sql
SELECT
    -- general profile vs full JD text
    e.embedding
        <-> CAST(:full_jd_vector AS vector)                          AS full_jd_distance,

    -- career narrative vs level/role text (falls back to e.embedding if NULL)
    COALESCE(e.resume_embedding, e.embedding)
        <-> CAST(:jd_level_vector AS vector)                         AS level_distance,

    -- skills profile vs required skills text (same column reused for preferred)
    COALESCE(e.skills_embedding, e.embedding)
        <-> CAST(:mandatory_vector AS vector)                        AS mandatory_skills_distance,

    COALESCE(e.skills_embedding, e.embedding)
        <-> CAST(:preferred_vector AS vector)                        AS preferred_skills_distance,

    -- certifications vs cert requirements text
    COALESCE(e.certifications_embedding, e.embedding)
        <-> CAST(:cert_vector AS vector)                             AS cert_distance,

    ts_rank(...) AS keyword_score
FROM team_member_embeddings e ...
```

Note: the table has **4 member vector columns**, not 5. `skills_embedding` is reused for both
mandatory and preferred distances — both compare JD skill text against the same candidate skills
column, just with different query vectors. The `COALESCE(..., e.embedding)` fallback means rows
where a specialized column is NULL (e.g. seed candidates) gracefully degrade to the general
embedding for that comparison.

And then `_compute_total_score()` combines them into a single composite score using
configurable weights (stored in `settings.py`):

```python
multi_vec_semantic = (
    full_jd_sim       * 0.25   # broad topic alignment
  + level_sim         * 0.35   # seniority / role level (now meaningful post ae8a036)
  + mandatory_vec_sim * 0.20   # required skills alignment
  + preferred_vec_sim * 0.10   # nice-to-have skills
  + cert_vec_sim      * 0.10   # certification match (0 weight when no certs required)
)
```

The cert vector had been computed and fetched but previously dropped before the weighted sum.
Adding it at 10 % weight means it contributes signal when certifications are required and adds
minimal noise when they aren't.

The `execute()` method was also refactored from a monolithic 200-line function into clearly
separated private helpers:

- `_extract_vectors()` — safely converts numpy arrays to lists with fallbacks
- `_build_keyword_strings()` — constructs BM25 `websearch_to_tsquery` strings
- `_build_filters()` — assembles SQL WHERE clauses and params dict
- `_build_sql()` — constructs the full SELECT
- `_compute_total_score()` — weighted combination of all signals
- `_filter_and_rank()` — applies the 40 % threshold and returns top-40

#### New settings added

```python
rag_weight_full_jd: float = 0.25      # was implicit 1.0 (single vector)
rag_weight_level: float = 0.35
rag_weight_skills_mandatory: float = 0.20
rag_weight_skills_preferred: float = 0.10
rag_weight_cert: float = 0.10         # new — cert vector now participates
```

#### Impact

- Retrieval now ranks candidates on overall fit across all five embedding dimensions rather
  than a single generic similarity.
- The cert vector contributes to ranking for roles that specify certifications.
- All five per-dimension similarities are stored on `RAGCandidate` and visible in the API
  response via `rag_signals` (see §2d).

### 2c. Refactor: Unified Skill Group Scoring

**Commit:** `4daabbd` — *refactor: unify skill group scoring and fix duplicate context computation*

**Files changed:** `src/app/ai/utils/scoring.py`, `tests/unit/test_scoring_agent.py`

#### The problem

Node 5 (`ScoringAgent`) had two separate scoring paths:
- `_calculate_mandatory_group_score()` for mandatory skills (with profile text fallback)
- Inline logic for preferred skills (no profile text fallback, different code path)

This meant preferred skills got slightly different matching semantics than mandatory skills for
no good reason — a skill found only in `profile_text` would count for mandatory but not for
preferred.

Separately, `_calculate_context_boost()` was called twice in `execute()` — once to compute the
aggregate context score and again to get the individual sub-scores for `score_dict`. This was
wasteful and meant the context sub-scores had to be duplicated in memory.

#### The fix

**Unified method:** `_calculate_mandatory_group_score` was renamed to `_calculate_skill_group_score`
and is now called for both mandatory and preferred groups with the same two-pass logic:

1. Check if any alternative skill ID is in the member's `member_skill_ids` (DB-level match)
2. Fall back to a whole-word regex search in `profile_text`

The regex pass was also hardened to prevent false positives on short tokens:

```python
_SHORT_ALLOW = {"s3", "c#", "f#", "r", "go", "ui", "ux"}

def _skill_found_in_text(self, members, text):
    for mem in members:
        if len(mem) <= 2 and mem.lower() not in self._SHORT_ALLOW:
            continue   # ignore single-char/ambiguous tokens
        pattern = r'(?<![a-z0-9_])' + re.escape(mem.lower()) + r'(?![a-z0-9_])'
        if re.search(pattern, text):
            return True
    return False
```

This prevents "git" matching "digital", "scala" matching "scalable", etc.

**Context boost fix:** `_calculate_context_boost()` now returns a dict containing both the
aggregate score and all sub-scores (experience, cert, location, work_mode, title). The caller
reads it once and spreads it into `score_dict`, eliminating the duplicate computation.

#### Test suite

`tests/unit/test_scoring_agent.py` was updated to call `_calculate_skill_group_score` (the new
unified name) and covers both mandatory and preferred paths.

### 2d. Feat: Expose RAG Signals in Scoring Response

**Commit:** `33c1fde` — *feat: expose rag_signals in matching scoring response*

**File changed:** `src/app/ai/agents/matching_scoring.py`

#### The problem

`RAGCandidate` carries five per-vector similarities and `final_similarity` (the composite RAG
score), but `score_dict` never included any of them. Debugging whether RAG retrieval was working
correctly required adding logging inside the RAG agent — there was no way to see RAG signals in
the API response.

#### The fix

Added a `rag_signals` block to `score_dict`:

```python
"rag_signals": {
    "final_similarity":     round(rag_candidate.final_similarity, 4),
    "jd_level_similarity":  round(rag_candidate.jd_level_similarity, 4),
    "mandatory_rag_sim":    round(rag_candidate.mandatory_similarity, 4),
    "preferred_rag_sim":    round(rag_candidate.preferred_similarity, 4),
    "cert_rag_sim":         round(rag_candidate.certification_similarity, 4),
},
```

This is purely additive — no scoring logic changes. It means every API response now carries the
full RAG-phase signal breakdown alongside the Node 5 scoring breakdown, making it straightforward
to compare retrieval-phase fit with scoring-phase fit.

### 3e. Feat: Real Gemma Embeddings in Seed Script + Populate skills_text

**Commit:** `081265a` — *feat: use real Gemma embeddings in seed script and populate skills_text*

**File changed:** `scripts/seed_candidates.py`

#### Problem 1 — Mock embeddings

The seed script was generating embeddings using a hash-based random number generator:

```python
seed = hash(f"{team_member['designation']}:{','.join(sorted(team_member['skills']))}")
rng = np.random.RandomState(seed % (2**31))
return rng.randn(3072).astype(np.float32)   # 3072-dim random, wrong shape
```

The vectors had the wrong dimension (3072 vs the pipeline's 768) and carried zero semantic
meaning, so similarity scores during testing were random noise.

**Fix:** Replaced with real Gemma embeddings using the same `GemmaEmbeddingAgent` that runs in
production:

```python
def generate_embedding_vector(team_member: dict) -> np.ndarray:
    agent = GemmaEmbeddingAgent(device="cpu")
    text = f"{team_member['designation']} with skills: {', '.join(team_member['skills'])}"
    return agent.embed_text(text)
```

#### Problem 2 — `skills_text` was never inserted

The `INSERT INTO team_member_embeddings` statement listed these columns:
`(team_member_id, embedding, profile_text, metadata, created_at)`

The `skills_text` column was not in the list. BM25 keyword search reads `skills_text` first; with
it NULL every candidate got the same keyword score regardless of their skill set. The bug existed
even when the seed CANDIDATES dict had full skill lists — the skills were stored in
`TeamMemberSkill` but never populated into the embeddings table.

**Fix:** Added `skills_text` to the INSERT:

```python
skills_text = " ".join(candidate["skills"])   # plain space-separated for tsvector

INSERT INTO team_member_embeddings
(team_member_id, embedding, profile_text, skills_text, metadata, created_at)
VALUES (:team_member_id, :embedding, :profile_text, :skills_text, :metadata, :created_at)
```

#### Problem 3 — Re-running the script did nothing for existing records

The old script did `continue` as soon as it found an existing `TeamMember`, so re-running after
a code change would skip every candidate and not fix the NULL `skills_text` in existing rows.

**Fix:** Restructured the loop so TeamMember and skill creation is guarded by the existence
check, but the embedding row is **always** deleted and re-inserted:

```python
if existing:
    print(f"↩  {candidate['id']} profile exists — refreshing embedding")
else:
    # create TeamMember and TeamMemberSkill rows ...

# Always: delete stale embedding and insert fresh one with skills_text
db.execute(text("DELETE FROM team_member_embeddings WHERE team_member_id = :id"), ...)
db.execute(insert_sql, {..., "skills_text": skills_text, ...})
```

This means `python scripts/seed_candidates.py` is now idempotent and safe to re-run to refresh
embeddings whenever skill data or the embedding model changes.
